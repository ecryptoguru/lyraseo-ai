# Provider ledger rehearsal

Run `pnpm test:provider-ledger` after `pnpm db:local` has provisioned the existing local PostgreSQL roles. The gate independently checks the Docker image and loopback binding, creates fresh `template0` databases with random names, and never resets an existing database. It applies the checked-in migrations, registers the owned fixture database on this exact postmaster, runs restricted-role tests, replays the accepted 27-migration baseline with populated financial history, and rejects unsafe purpose-role configurations in a separate socket-only PostgreSQL instance. Successful owned databases are dropped; failed ones are named and retained for diagnosis.

The table and function boundary is `lyraseo_ledger`. The no-login `lyraseo_ledger_owner` owns narrow functions, never product tables or a database. The local `lyraseo_ledger_fixture` login has only explicit function grants. Enrollment is administrator-only and additionally requires a registered `lyraseo_ledger_<12 hex>` database and synthetic sponsor/route/tariff identifiers. Customer GUCs cannot enroll or execute managed financial transitions. All fixture qualifications have live execution disabled.

`ProviderAttempt` concepts are persisted in `attempt`, with immutable preparation revision, request hash, operation fence, correlation identity and provider-account task binding. `attempt_event`, `settlement`, and `adjustment` are append-only evidence. A prepared request is persisted before submission. Only an inserted intent returns `submissionGranted: true`; replay returns the original attempt with `submissionGranted: false`. A replay does not authorize another network submission. The public service module contains no transport or credentials.

Acceptance, result validity and financial certainty are separate. An accepted charged POST can remain pending; a poll does not refund it. An unknown charge retains its reservation. A definitive failed attempt may admit at most one replacement inside the original reservation, including exposure for unstarted planned steps. Closing a plan prevents further attempts. Settlement derives cost and accepted-output count from saved evidence, releases the original reservation once, and records an explicitly named application settlement key. Later corrections append signed differences while leaving the original UsageReceipt unchanged. The original UTC admission month and $10 combined/$8 Azure/$1 Parallel/$1 DataForSEO partitions remain in force. Keyword enrichment does not consume consumer-observation units.

The shared `apply_budget_change` function is SECURITY INVOKER and is also used by legacy `settleOperation`; it adds no execution authority. Generic runtime financial writes are fenced for enrolled synthetic owner/periods. That conservative fixture fence deliberately prevents mixing unmanaged jobs into a managed fixture account. Real product accounts are never enrolled by this gate.

The six adapters in `fixtures.ts` are network-free synthetic examples, not recorded customer responses, provider invoices or current tariffs. They exercise Azure editorial/API observation, Parallel Search plus Extract, consumer ChatGPT/Gemini Standard, and keyword batches. Actual provider support, account eligibility, prices, rights, safe request bounds and hosted execution remain separate release gates.

Keyword selections freeze an existing GSC opportunity, exact measured URL, evidence/window, selected keywords and requested English/India market. The live quote is explicitly unavailable: `maximumCost: null`, `quoteId: null`, `dispatchable: false`. A selection never creates a paid operation. Saved results retain source, method, currency, market and collection time. Synthetic result writes require a completed same-scope managed fixture operation bound to the selection hash; reopening a saved result performs no provider request. Source expiry is preserved, not recomputed on read. Declining-click selections use the same comparable-window helper as the opportunity engine and GSC read path; both snapshot identities, windows and provenance are frozen, and the earlier source expiry governs the selection.

Deletion integration must withdraw KeywordEnrichmentResult before KeywordSelection. The immutable guard permits DELETE only by the separately provisioned `lyraseo_deletion_owner` for an already tombstoned exact site; the privacy migration must grant its narrowly scoped erasure path. Financial evidence has no such exception. The provider ledger stores hashes, bounded usage/status and financial/task identities, never prompts or raw answers.
