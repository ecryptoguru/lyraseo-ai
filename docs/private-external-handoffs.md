# Private-pilot external handoffs

The current capability supports private destination setup, exact draft previews, saved handoff intents and redacted history. All product intents are **QUARANTINED**. It does not send to WordPress or a customer webhook receiver. Live delivery remains unavailable until a separately admitted kernel action, hosted egress/secrets and controlled destination acceptance are qualified. Setting a feature flag cannot enable a send path.

The site route is `/app/sites/<siteId>/handoffs?workspaceId=<workspaceId>`. The same authorized repository services serve the page and `/api/integrations/handoffs`. Reads use current verified actor/site permissions. Only interactive owners/admins with recent authentication can manage destinations, rotate keys or prepare a test. Granted editors can review and save an exact same-site draft handoff. Clients/viewers can read their granted site's saved history; API/MCP read credentials receive no write authority.

`handoffs` in `LYRA_ENABLED_CAPABILITIES` enables setup and saved-intent writes after migration. Independent operator pause retains read access and disconnect. `LYRA_HANDOFF_ENCRYPTION_KEY` must be an independently generated, canonical base64-encoded 32-byte key stored in the host secret manager. It is never returned to the browser. Missing encryption configuration leaves saved-history reads and disconnect usable. Existing Google keys are not reused. Connection secrets use AES-256-GCM with associated data binding purpose, workspace, site, destination URL and generation.

## WordPress

An owner/admin confirms the installation on the site's verified HTTPS origin and provides a dedicated WordPress username/application password. Setup stores encrypted credentials; it makes no identity/capability request and does not claim the connection has been verified. The installation may include an explicitly chosen subdirectory and must end in `/`.

The user reviews one immutable saved draft revision. Rendering treats the authored body as literal escaped paragraphs, fixes `status=draft` and fixes the posts endpoint. The intent freezes exact request bytes, their SHA-256 hash, renderer version, source revision, source draft and destination generation. A later renderer version cannot change those bytes. Saving retains the deliberately reviewed authored copy under the saved-work lifecycle until deletion; it does not copy an audit capture or full AI provider envelope into the handoff.

A send barrier is durable before any socket. An accepted request with a lost acknowledgement becomes **UNRESOLVED**. A worker restart, repeated queue claim or new idempotency key cannot silently create a replacement for the same saved draft. Reconnecting a destination does not clear that uncertainty. Before any future delivery, inspect WordPress manually and use a separately qualified reconciliation action. Confirmed IDs are positive safe integers; editor links are built on the selected installation rather than trusting a returned URL. Core draft updates are unavailable because the documented REST update interface does not provide the required atomic draft-state guard. Disconnect removes local credentials and revokes future work; it never deletes or publishes a remote post.

## Webhooks

Owners/admins explicitly confirm a public HTTPS receiver without URL query secrets and choose whether to save `audit.completed` and `report.created` events. Registration sends no test. Resource events are created transactionally with the source transition, remain quarantined, and contain only an opaque event ID, type/version, time, scope and resource identity. A queue overflow is recorded as a terminal `QUEUE_LIMIT`, without rolling back the audit/report. Explicit test intents are separate synthetic test events.

The current signing contract is HMAC-SHA256 over `ASCII(unix_seconds) + '.' + exact UTF-8 body bytes`. Headers are `X-Lyraseo-Timestamp`, `X-Lyraseo-Key-Id`, `X-Lyraseo-Signature: v1=<hex>` and `X-Lyraseo-Event-Id`. The event ID inside the authenticated body is authoritative. Read raw bytes before parsing; reject malformed/duplicate headers and timestamps outside the symmetric 300-second window; compare decoded MAC bytes in constant time; then validate the bounded envelope and deduplicate its ID atomically before receiver side effects. A successful duplicate may return 2xx. A valid signature alone does not provide receiver deduplication.

A key is shown once. Rotation retains at most one previous key for at most 24 hours; the sender's optional previous-key headers support an explicit receiver transition. Receivers must also retire old keys on their own expiry schedule. Disconnect invalidates generation and deletes current/previous local signing material. It cannot retract a receiver's already-delivered copy.

At-least-once retries retain identical event/body bytes and use a fresh signature timestamp. Network uncertainty, 429 and 5xx use delays of 1 minute, 5 minutes, 30 minutes, 2 hours and 12 hours, for an initial attempt plus at most five retries. Other 4xx and redirects are terminal; no redirect is followed. Leases fence old attempts and stale receipts cannot change a new attempt's outcome. A lost acknowledgement consumes its attempt and retains the applicable backoff rather than immediately repeating a POST. Receipts store only coarse outcomes/status/times, not response bodies or secret headers.

## Egress and local evidence

The JSON adapter shares acquisition's all-answer public-DNS validation, pins the selected address to the direct socket, preserves original Host/TLS identity, follows zero redirects and rechecks current authority before DNS and immediately before the socket. A single ten-second deadline covers authorization, DNS, socket and response streaming. Limits are 16 KiB response headers, 64 KiB response body, identity encoding, 16 KiB event bodies and a 512 KiB reviewed WordPress payload. Cancellation can abort an in-flight request; it cannot retract bytes already sent.

`pnpm test:handoffs` is a required CI gate. It creates uniquely named owned databases in the validated loopback PostgreSQL 17 container, applies empty and populated migrations, uses actual restricted runtime/fixture logins, and runs controlled HTTP acceptance/uncertainty tests through the production adapter with a test-only final socket seam. The fixture functions require a separately enrolled local database OID/postmaster and FIXTURE rows. Product callers cannot promote quarantined rows, call fixture functions, read encrypted secret columns or mutate receipts. Fixtures are synthetic; they do not qualify hosted TLS/egress or a real WordPress account/receiver.

Deletion migration 32 can call `lyraseo_handoff.retire_site(workspace, site)` immediately after a site tombstone to retire generations and remove keys, then `lyraseo_handoff.erase_site(workspace, site)` for local handoff cleanup. Only `lyraseo_deletion_owner` receives these functions; browser and maintenance logins have no direct execution privilege. Both require a tombstoned site. Erasure removes local bodies, URLs, connections and receipts, and reports external copies as `USER_MANAGED`; it asserts no remote deletion.

Remaining release gates: review and admit explicit external-write kernel actions; hosted runtime egress/secrets/cancellation qualification; independently enabled transport configuration; controlled real WordPress draft-create and receiver verification; separately audited WordPress reconciliation; private authenticated browser walkthrough; exact integrated-head CI. No live send, deployment, paid provider request or production acceptance is implied by local fixtures.

WordPress semantics were checked against the [official posts reference](https://developer.wordpress.org/rest-api/reference/posts/) and [application-password authentication guidance](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/) on 2026-11-03.
