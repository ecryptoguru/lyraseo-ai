# Live observation execution: current gates

Status: **not implemented and not enabled**. This note records the live-path work still required after the observation preflight and synthetic protocol rehearsal. It does not authorize a provider call. Azure API observations, consumer ChatGPT observations, and consumer Gemini observations are separate surfaces; requested English/India settings do not prove provider support for that market.

## Existing boundaries

- `apps/lyraseo-web/src/app/api/visibility/route.ts` rejects `request-run` with 503. `apps/lyraseo-web/src/server/providers/observations/requests.ts` returns unavailable even if passed a caller-created qualification object. The preflight returns no executable quote.
- `packages/db/src/accounting.ts` contains actor-scoped quotes, atomic admission, per-user UTC budget partitions, lease and outbox mechanics. `issueOperationQuote` takes a caller-supplied price, route, input and tariff version, so it must be called only by a new trusted, server-owned qualification and price calculation path; exposing it directly does not qualify a price. An admitted operation alone is not proof of a paid provider attempt.
- `202611030007_provider_attempt_ledger` and `packages/db/src/provider-ledger.ts` are explicitly fixture-only. Qualification cannot be live-enabled, accepted event namespace and settlement provenance are synthetic, and the restricted fixture role cannot be repurposed for customer receipts. `202611030012_provider_observation_binding` binds only reviewed synthetic fixture panel slots. Preserve these guards; add separately audited live capabilities and roles instead of changing fixture evidence into real evidence.
- `packages/db/src/observation-source.ts` and `202611030003_private_observation_artifacts` accept `CONTROLLED_FIXTURE_V1` and `synthetic=true`. The existing MAC and source provenance describe the controlled fixture producer, not provider bytes. The private source producer, retention and publication contract require a distinct live provenance path. It must not accept a browser-supplied response, a generic JSON object or a self-asserted hash as provider evidence.
- `apps/lyraseo-worker/src/index.ts` has no observation collector. Its queue entry point alone does not supply an independent provider credential, provider egress identity, or receipt-signing authority.

## Required production path

1. Create an independently provisioned carrier identity which alone can access the chosen provider credential and whose authenticated receipt channel is independently verifiable by the ledger/source producer. Isolate its signing authority and provider credentials from the public web process and ordinary worker runtime. Responses from Azure and DataForSEO are authenticated by TLS to the carrier; they are not independently provider-signed statements. A carrier signature attests what that isolated carrier observed; it is not a provider signature. Fixed provider origins, normal TLS hostname validation, no automatic redirects, bounded bodies/timeouts and secret-free error logs are required.
2. Persist a reviewed, revocable qualification for each actual account, surface, deployment/model and English/India setting, including supported request features, source/retention rights, tariff version, currency, validity period, and independently bounded token/tool/task costs. Derive prices and scope server-side from that record and the immutable panel; never accept the cost, provider origin, deployment, rights or qualification from a customer request. Deny new quotes if any required qualification expires or is paused. Azure grounding/tool charges need an actual conservative upper bound; if a bound cannot be established, do not admit the grounded operation.
3. From an authorized, currently verified site and reviewed panel, issue a short-lived quote that freezes slot IDs/versions, requested surface, language/market, qualification and tariff versions, provider-specific maximum and count, and operation input. Atomically admit the approved quote through existing combined/provider/count partitions and queue publication. Admission must be idempotent, and two independent connections must not overspend. A replay or polling read must not create provider work.
4. Give a carrier a short-lived, single-use, authenticated authorization bound to the persisted operation, site, panel revision, slot, attempt, fence, provider/account, immutable request hash and deadline. The carrier must recheck revocation, pause, lease and budget authorization immediately before the socket opens. Persist the durable submission intent before egress. A lost or expired worker fence cannot authorize another POST. A retry after a request may have crossed the network must reconcile first, never assume non-acceptance from a timeout.
5. The carrier records bounded original response bytes or a retained private immutable artifact according to the approved rights, their hash, received time, status, selected safe headers and request/account/attempt binding. Atomically ingest a carrier-authenticated acceptance, uncertainty, or result event through a new live-only ledger principal; deduplicate by provider/account/task/event identity and reject changed bodies for a replay. Provider-response identifiers and the request hash must link all corrections to the original attempt. Keep unknown cost unknown; provider-reported numeric cost and rate-card estimates must have distinct provenance. Late cost corrections must preserve receipts and adjust accounting once.
6. Reconciliation runs under its own renewable lease and bounded retries. A known accepted task may be polled using the correct profile/account. Ambiguous POSTs, unsupported results, timeouts, expired provider data, revoked credentials and unavailable evidence remain distinct. A missing listing or absent ready task is not proof that no task was accepted or billed. Maintain a visible operator recovery state and do not release a reservation while a charge remains unresolved without an approved final accounting policy.
7. Add a distinct provider source producer which verifies the carrier receipt, the saved panel/slot/account/attempt binding, the acquired response bytes and qualified usage rights before writing private evidence. Preserve the actual collection method, model/surface, timestamps, requested and confirmed locale separately, prompt slot coverage, determinate/ambiguous/failed state and citations. Publish only after all authorization and retention checks succeed. Do not let receipt capture, settlement or revoked-access cleanup invent a measurement or lose a genuine provider charge.
8. Enable each surface independently only after its schema/read paths and live controls pass, first for staff and then the private pilot. Keep disconnect and pause independent. Recheck the quoted scope, latest principal and qualification during dispatch; retain saved evidence on pause without starting a replacement operation.

## Provider-specific recovery constraints

- Microsoft documents Responses creation at a configured Foundry resource's `/openai/v1/responses`, with Azure deployment name in `model` and either API key or Microsoft Entra authentication. Retrieval requires a response ID. Its documented background mode requires `store=true`, and its retention and permitted usage must be qualified; the current synthetic `store:false` example does not establish a recoverable background workflow. A timeout before obtaining the response ID remains ambiguous unless an independently qualified provider/account mechanism resolves it. See [Azure Responses API reference](https://learn.microsoft.com/en-us/rest/api/aifoundry/azureopenai/responses) and [Azure Responses background requirements](https://learn.microsoft.com/azure/ai-services/openai/how-to/responses?tabs=rest).
- DataForSEO documents separate Standard ChatGPT and Gemini task creation. The current parser is an offline schema rehearsal, not account or market qualification. The [ChatGPT tasks-ready endpoint](https://docs.dataforseo.com/v3/ai_optimization/chat_gpt/llm_scraper/tasks_ready/) describes completed task IDs and user tags; absence from a completed list cannot settle whether an earlier POST was accepted. Qualify an actual account's result retention, correlation and reconciliation behavior separately for each consumer surface before using them for recovery.

## Required verification before any live enablement

Use deterministic mocked provider responses and disposable PostgreSQL with restricted, independent web, carrier, receipt/source and maintenance principals. Exercise forged browser responses and signatures, wrong account/slot/fence, stale or revoked quotes, duplicated delivery/receipts, two concurrent reservations, pause and revocation immediately before egress, accepted-then-crash recovery, missing initial response, ambiguous timeout, pending/late/corrected charges, invalid or duplicate JSON keys, provider 429/5xx, unsupported market, missing rights, unreadable/expired source, and separate planned-slot coverage. Verify no fixture principal can mint a live receipt or publish a live source and no carrier receipt can confer another site's access. Preserve raw failing evidence.

After these local tests pass, bounded live acceptance still requires a real eligible account and credentials, approved tariffs and collection/storage rights, a provisioned isolated carrier identity and signing key, verified endpoint/deployment and supported market, and a live test within the user's authorized scope and spend. Record actual environment, dates, provider receipt/source comparison and cost. Those external gates are distinct from the currently missing local implementation; satisfying credentials alone does not make the product ready.
