# Private-pilot authentication and ledger setup

This tranche adds application code and local PostgreSQL proofs. It does not provision a Supabase project, configure Gmail/Google, spend provider credit, enable public signup, or complete production acceptance. Use a dedicated LyraSEO AI project and accounts; never reuse LyraShield resources or secrets. Supabase Free is the initial target. Do not upgrade to resolve a failed prerequisite without approval.

## Configure an approved dedicated free project later

1. Apply the checked-in Prisma migrations with the migration credential. Prisma manages product tables only; it must not migrate or write Supabase's managed `auth` schema. Keep the database migration credential outside the web runtime.
2. Create separate non-owner, non-superuser, non-BYPASSRLS runtime and identity roles. Adapt the local script's grants to the chosen role names, using separately generated secrets in an authorized secret store. The runtime needs product-domain access as shown in that script; it must not modify `ProductUser`, `ProviderIdentity`, or `StaffGrant`. The identity role needs `SELECT, INSERT` on `ProductUser`/`ProviderIdentity`, and `SELECT, INSERT, UPDATE, DELETE` on `AuthThrottle`/`ProductSession`. Neither role gets arbitrary managed-auth writes. Browser `anon`/`authenticated` roles get no product-table grants.
3. Inspect the actual project schema before granting managed session metadata. On the live project, the operator can grant column-level `SELECT (id,user_id,created_at,refreshed_at,not_after) ON auth.sessions`, but cannot grant schema-level `USAGE ON auth`. Apply `scripts/sql/supabase-session-metadata.sql` as the project operator to create a private `security_invoker` view. It retains the caller's underlying column permissions and exposes only those five fields through `lyraseo_private.session_metadata`; no tokens, managed-auth writes, definer privilege or browser access are added. The app uses that view. Normalize the provider's timezone-bearing creation/deadline fields to UTC timestamps; `refreshed_at` is already stored as UTC without timezone. This also avoids Prisma's assumption that returned timestamps use UTC. Missing/unsupported metadata must keep authentication unavailable; never substitute a page-click time or refreshed JWT `iat`. PostgreSQL documents these [invoker-view and schema lookup rules](https://www.postgresql.org/docs/17/sql-createview.html).
4. Configure Google OAuth with the exact approved application origin and `/auth/callback`. Configure email OTP with Gmail SMTP in the Supabase dashboard, a 10-minute OTP expiry, and an email template containing `{{ .Token }}`. Disable public email signup and anonymous sign-ins. Pre-create invited email users through the operator's authorized provider console; the application sends OTP with `shouldCreateUser:false`. Google identities are still subject to the server's explicit pilot email allowlist before product access.
5. The server also records token-free product session history: provider session ID, stable product user, security version, original creation time and last accepted provider refresh time. A new history row requires a fresh signed first-factor sign-in; an existing seven-day-stale row is refused even if the provider has just refreshed the cookie. Page visits with an unchanged provider refresh timestamp never extend the window. This deliberately measures refreshes observed and accepted by this application. A refresh made only through another client cannot revive an expired product session; sign in again. This is conservative where the provider does not supply refresh-gap history. Retention cleanup of expired session rows is still pending; never delete history while the corresponding provider session could remain valid.

6. Set access-token expiry to 900 seconds. Application policy checks a 30-day maximum session, seven days since successful refresh, provider `not_after`, verified current user, signed claims, first-factor AMR and MFA. Free-tier native session controls are not assumed. If the project's metadata cannot enforce the approved policy, leave access disabled and report the prerequisite. The policy does not claim to revoke the provider JWT across unrelated services; product tables have no browser access.
7. Set the server environment using `.env.example`: `LYRA_AUTH_ENABLED=true`, exact `APP_ORIGIN`, dedicated Supabase public URL/key, restricted `DATABASE_URL`, separate `AUTH_DATABASE_URL`, and comma-separated `PILOT_ALLOWED_EMAILS`. HTTPS is required for remote origins. Public Supabase keys are public identifiers; DB credentials and all provider secrets stay server-side. Authentication is explicitly off unless all prerequisites exist.
8. Build with the intended environment and verify the actual hosted flow separately. The session adapter uses provider `getUser()` and signature-verified `getClaims()`, not decoded browser claims or editable metadata. Product accounts use `(provider,subject)` and a stable generated product ID; email is only an invitation check, never an identity merge key. Workspace membership is never auto-created from a Google profile.

## Operator and MFA checks

Customers can enroll an authenticator (and a separate backup) at `/app/security` after a fresh sign-in. Enrollment and owner changes require authentication within ten minutes; an MFA-enabled actor also needs recent verified MFA. Once enrolled, either Google or email first-factor login must be followed by TOTP. Sign-in offers the currently verified authenticator choices, including the backup, and verifies the chosen factor against the provider-owned list. Do not assign a staff grant until the operator has enrolled MFA and tested it. Staff grants are explicit database/operator assignments and cannot be self-issued by the web role.

Single-use owner-change grants are hashed, bound to user/session/action/workspace, and consumed in the membership transaction. The workspace row lock prevents concurrent demotions/removals from leaving no active owner; suspended accounts do not count as surviving owners. Any future suspension workflow must take the same workspace locks and preserve this invariant. Editors/viewers only see granted sites; viewers cannot run jobs. Deleted scopes and suspended/stale-security-version actors are denied.

The approved 72-hour operator recovery hold, account-recovery workflow, invitations administration, retention cleanup and recovery audit trail are still to be implemented. Do not use database edits as a customer-facing recovery feature or claim those acceptance gates pass. If Supabase internally links Google/email to the same provider subject, that remains a provider identity; the product does not merge two distinct subjects by matching email. Verify provider linking behavior in acceptance testing.

## Job and budget accounting boundaries

The internal service reserves exact decimal USD against actual plus committed costs, atomically with the operation and outbox. Limits remain $10/user/UTC month: Azure $8, Parallel $1, DataForSEO $1; 25 API observations and 100 ChatGPT plus 100 Gemini consumer observations. Allowances span the user's workspaces, with no rollover/borrowing or extra content/research monthly quotas. A server-owned, bounded tariff/quote must exist before any paid admission endpoint is enabled. The browser cannot supply a budget owner or maximum cost. No paid admission or provider dispatch endpoint exists in this tranche.

The durable outbox can be replayed; a job lease/fence and recorded attempt intent prevent an ambiguous dispatch from being blindly retried. Only one expensive operation per user may run at once. Cancelling/expiring undispatched work (including an expired, no-attempt job whose worker crashed after claim) releases commitment; dispatched/uncertain work retains it until reconciliation. Known provider acceptance can be recorded with the same fence after lease expiry or account revocation; this cannot issue another request. Provider receipt settlement records actual charges even for failed output and after access revocation, without granting new work. This internal financial receipt path is not a customer endpoint. Duplicate receipt replay is idempotent; mismatched receipts fail. An overrun is recorded honestly and marked for reconciliation, never erased to make a cap appear satisfied. A monthly consumption guard is not a guarantee against provider-side billing errors or an unexpected charge.

Cloudflare queue publishing, scheduled cleanup, acceptance reconciliation with a live provider, dead-letter operation, trustworthy quotes and provider execution remain unconnected. Outbox helpers are primitives, not a running worker. Backups, restore and end-to-end failure recovery remain separate acceptance gates. Expired auth-throttle rows must be cleaned by the eventual scheduled retention worker; they contain hashed identifiers, counters and expiry, not raw email/code contents.
