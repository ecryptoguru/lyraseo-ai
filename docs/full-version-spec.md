Auth phase boundary: Supabase details below describe private phase-one testing. Better Auth must be ready before the first customer launch. Proposed layout: `apps/lyraseo-web`, `apps/lyraseo-worker`, `packages/visibility`, `packages/db`, and `packages/contracts`. Keep rules/scoring independent of database, browser provider, UI, auth and model SDKs. A folder is not a separately deployed service unless there is an operational need.

Next.js integrates Supabase Auth and runs product APIs on Vercel's Node runtime. Use the supported Supabase SSR cookie/PKCE flow and pin the integration version after compatibility review. Supabase owns identity, auth records, token issuance and refresh; LyraSEO AI owns workspace membership, site grants and product authorization. Product data is accessed server-side through Prisma. Do not expose administrative database credentials or Supabase secret/service-role keys in browsers. A Supabase login does not automatically populate PostgreSQL claims for direct Prisma connections: product queries require verified identity and explicit workspace/site ownership predicates. Restricted database roles and RLS add defense where their session context is proven. The engineering contract specifies scoped transactions and non-owner/non-BYPASSRLS product runtime roles; verify their behavior with the chosen driver/pool.

Prisma owns the product schema and its migration history, including SQL constraints, policy definitions and required indexes. Supabase manages the `auth` schema; product migrations must not recreate, alter or drop Supabase-managed auth objects. Use a stable LyraSEO AI product-user ID for ownership, memberships and budgets. Link it to the phase-one Supabase UUID `auth.users.id` through a reviewed provider-identity mapping; add the Better Auth identity mapping at cutover without changing product-user ownership or duplicating budget allowances. Prisma product IDs can remain cuid values. Review auth-user deletion alongside workspace ownership and financial-record retention rather than blindly cascading whole workspaces. Schema introspection and migration checks must preserve this ownership boundary. Runtime pooled connections and migration/admin connections are separate. Cloudflare gets a compatible PostgreSQL driver adapter and Node compatibility settings; Vercel and Workers each get bounded connection configuration. Do not add Accelerate, Hyperdrive or Redis automatically; add one only if measured connection/runtime needs justify it.

Admission transaction: authorize actor/site and entitlement, validate manifest/request, create operation and reservation, and write an outbox event. A LyraSEO AI dispatcher delivers the outbox to dedicated queues, retrying without losing or double-admitting work. Consumers load persisted ownership/scope, acquire a lease, execute bounded checkpoints, persist immutable output, and settle once. Queue payloads carry references, never authority to alter owner or limits. Checkpoint provider receipts to bound duplicate external work after crashes; at-least-once delivery cannot promise exactly-once external API calls.

Browser, model, PDF generation and provider calls never block a web request for the entire job. Private artifacts remain in R2; short-lived downloads require fresh authorization. Job progress comes from persisted status, initially by bounded polling. Cancellation is a durable flag acknowledged by execution, not an optimistic UI-only state.

The rationale is to start with one primary database and colocate database-dependent web compute in Mumbai, given the India-based business serving India and global customers. This is an engineering recommendation, not a conclusion that most customers are in India or a measured global-latency result. A global CDN improves public/static delivery; authenticated database work still reaches the primary region. Keep staging/test projects, buckets, credentials, auth origins and queue namespaces isolated, with the same intended core geography where supported. Select the exact Supabase region rather than the general APAC grouping, which is not a Mumbai guarantee.

Alternatives: Singapore for a broader Southeast Asia focus, or Frankfurt if the founder expects a predominantly European customer base. Either alternative should move the primary database and web functions together. Do not add read replicas, multiple writable regions, an extra database or automatic geographic failover before measured needs and approved budget justify them. A single primary region has a regional-outage dependency; backups and tested restoration are separate requirements, not a claim of automatic failover. Do not add a connection proxy solely because the vendors offer one; first validate the existing driver and pool configuration.

Region selection controls only the selected service boundaries. Support tooling, logs, backups, global execution, email, billing and AI providers may involve other locations under their contracts. R2's `apac` is a hint; its published jurisdiction options do not establish India-only storage. PostHog EU is a telemetry-storage choice, not proof of regulatory compliance. Retention/deletion defaults are approved in the retention policy; processor/data-flow verification, legal applicability, Azure deployment scope and phase-two telemetry consent/settings remain checks to resolve.
