# Editorial provider fixture protocol

This protocol is a local, synthetic-only contract for testing how an editorial proposal could be prepared and parsed. It does not dispatch a request, authorize a user or site, issue a quote, reserve or settle a budget, persist a proposal, retrieve research, or enable the customer generation endpoint. The existing deterministic templates remain the available editorial assistance. Live generation and research remain unavailable until their separate authorization, accounting, provider, persistence, and acceptance gates are implemented and verified.

The request shape follows the `text.format` JSON Schema pattern in the [Azure structured outputs documentation](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/structured-outputs), with response parsing informed by the [Azure Responses API reference](https://learn.microsoft.com/en-us/rest/api/microsoft-foundry/azureopenai/responses). These references do not establish eligibility or support for a particular account, region, deployment, model, schema, or `store: false` setting. No live provider check was performed.

The fixture builder accepts a synthetic evidence snapshot containing both a context revision reference and its declarations; it rejects an independently supplied context object. Its versioned fixture fingerprint covers the projected evidence and normalized declaration contents, so changing those contents changes the fingerprint. This binds the supplied contents within the fixture only: it does not authenticate the revision, prove that a database captured the contents, or authorize a caller. Existing saved snapshots contain only the context reference, so this fixture input is not a production capture contract and cannot be constructed directly from a saved snapshot. A future path must securely capture and authenticate declarations with their revision and site before dispatch. It projects selected audit and Search Console evidence, rather than original HTML, and excludes workspace and site scope identifiers from the request. Source content, context, user instructions, and any provider response remain untrusted. No instruction in them grants permission or can authorize tools. External research requests fail closed; this fixture does not create or verify research sources.

The parser binds responses to the original in-memory prepared fixture and rejects ambiguous, malformed, duplicate-key, oversized, incomplete, refused, or unsupported output. Each section must be labelled as a source-linked recommendation or an assumption. A source identifier establishes a proposed association, not factual entailment: a person must verify every claim, including the unverified title, against the cited evidence before use. The text must be treated as untrusted content by any future interface, export, or publishing integration. The returned text digest covers the extracted response text only; it is not a wire receipt or proof of provider origin.

The request byte ceilings and output-token limits are conservative fixture bounds, not a tokenizer, a tariff, a cost estimate, or proof that a provider accepts a request. Fixture usage values are accepted only when internally consistent and are not billing evidence; cost is always unavailable. The in-memory binding cannot be serialized as a durable operation or recovered after restart. No fixture output may be represented as an authorized live observation or production provider receipt.

Before connecting a production path, independently implement and test current site authorization and revocation at dispatch and result access, approved server-issued quotes, the appropriate Azure partition and reservation, provider receipt handling and ambiguous-timeout reconciliation, durable frozen evidence and provenance, retention and deletion, idempotent settlement, explicit user action, editable/rejectable drafts, and bounded live acceptance. Verify current provider support, tariffs, data handling, account eligibility, and terms. Explicitly requested external research also needs an independently authorized source-ingestion and citation lifecycle, plus its own provider partition and quote; it must never be inferred or performed automatically from this fixture.
